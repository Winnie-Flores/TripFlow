## 演示前检查

- 提前安装依赖并运行 `npm run dev`，打开 `http://127.0.0.1:5173/#planner`。全程使用同一浏览器配置及访问地址，投影使用桌面布局。端口与保存位置见[运行说明](../README.md)。
- 用专门的演示旅行预置一份 **武汉两日** 行程。第 1 天放黄鹤楼和户部巷，第 2 天留空。确认地图中能定位昙华林，方便现场将它拖入第 1 天末尾。第 1 天先使用统一步行。预设出发时间和至少一站预约，以便展开时间轴时直接讲解。
- 预先导出这份旅行的 JSON，便于彩排后恢复起始状态。检查一份可离线打开的行程 HTML 或 PDF，作为导出展示备用。
- 预置一份“已去过”的杭州记录，武汉保留“规划中”。提前打开“旅行记录”并展开足迹地图，确认杭州绿、武汉橙，随后回到规划页。预先保存一张来自本项目真实联调的道路截图和一张足迹截图，在文件名或查看窗口明确写上“联网验收截图”。手边没有截图时直接使用备用口播。
- 检查底图、已有两站的真实道路结果、标记拖放、“路线与交通”、“预计时间轴”和导出预览。正文中不朗读固定距离或分钟数，以现场结果为准。
- 带计时器完整彩排一次。到 **4:35** 仍在等待时，跳过当前操作并切到技术讲解。成果段到 **7:30** 即收尾，剩余 30 秒留给切窗或停顿。截图、重试和备用段都算入原时段。

## 0:00–0:45 背景

操作：停在预置的武汉规划页，先不操作。

> 大家好，我展示的项目叫旅序 TripFlow，是一个自由行行程规划网页。平时做攻略，我们常常在地图里查地点，在备忘录里记顺序，再回到地图查两站之间怎么走。改一次安排，往往还要重新核对路程和时间。
>
> 旅序把这些操作放在一个页面。右侧找地点，左侧按天安排，拖一下就能把地图上的地点加入行程。接下来我以武汉两日游为例，展示从调整路线到保存和查看足迹的过程。

## 0:45–1:45 概要设计

操作：指向左侧行程、右侧探索与地图、顶部的“旅行记录”。屏幕可配一张简图，按“地点 → 游览 → 日期 → 路段”顺序指示。

> 界面分成两个入口。当前规划用于安排每天去哪里，旅行记录用于打开不同的旅行。桌面左侧是每日行程，右侧是搜索和地图。手机上可以切换这两个视图，通过按钮安排地点。
>
> 在数据上，我把地点和一次游览分开。一个地点有自己的坐标和标记样式，每次到访有单独的备注、停留时间和预约。同一家餐厅可以在一天里安排两次。日期记录当天游览的顺序，也可以指定出发和入住酒店。
>
> 页面由 React 组织，编辑状态由 Zustand 管理。高德负责查找地点和计算道路，编辑内容自动保存在当前浏览器。下面直接演示操作。

## 1:45–4:45 操作演示

### 1:45–2:25 从地图添加地点

操作：拖动昙华林标记到第 1 天末尾的插入区。放下后指一下卡片和地图编号。

> 这里已经安排了黄鹤楼和户部巷。现在我把右边的昙华林拖到第一天最后。出现插入提示后松手，左边就多出一张游览卡片，地图上的编号也随顺序更新。这个动作安排的是一次游览，地点仍保留在原来的地图坐标上。

### 2:25–3:10 跨天移动、撤销和交通方式

操作：用昙华林卡片的手柄拖到第 2 天空白区，点击顶部“撤销”。选中第 1 天，展开“路线与交通”，把第一段改为驾车。道路请求进行时继续讲，不连续点击重试。

> 我把第三站移到第二天，再按撤销，它会回到原来位置。接下来把第一段改成驾车，后一段保持步行。各段可以按实际出行方式设置。地图会重新计算当天道路，面板显示每段的距离、交通时间和已完成段数。

### 3:10–4:00 时间轴与导出

操作：展开第 1 天“预计时间轴”，指向到达、等待和离开时间。点“导出可读行程”并展示预览，然后关闭。现场只展示入口，下载和打印文件已提前准备。

> 时间轴从设定的出发时间开始，把交通、停留和预约等待合起来。早于预约到达时，可以看到中间要等多久。如果有路段尚未算完，后续时间会显示下限。
>
> 预览里可以看到每天的地点、预约和备注。这份行程可以下载成离线 HTML，也可以从系统打印窗口保存为 PDF。

### 4:00–4:45 旅行记录与刷新恢复

操作：进入“旅行记录”，展开足迹地图，指向武汉和杭州。若底图未及时出现，展示卡片状态即可。重新打开武汉旅行并刷新一次，指向已保存的地点顺序。4:35 后直接收尾。

> 这里是多次旅行的记录。武汉仍在规划中，对应橙色。杭州手动标成已去过，对应绿色。点城市可以筛选对应旅行。
>
> 我重新打开武汉这份旅行。刷新后，刚才安排的地点和分段方式可以恢复，在线道路会重新计算。也可以导出 JSON，作为这份旅行的可导入备份。

## 4:45–6:45 关键技术

### 4:45–5:25 两类拖动使用不同的提交方式

> 第一处是拖放。地图标记本身是可以拖动的 HTML 标签，放到日期里时只传地点 ID，然后由规划页创建一次游览。卡片排序用 dnd-kit，拖动期间先展示插入位置，放下才更新日期的游览顺序。跨天移动沿用原来的游览 ID，所以备注、预约和停留时间能一起移动。

### 5:25–6:05 控制路线请求和返回顺序

> 第二处是路线请求。每一天按照酒店和游览顺序生成相邻路段，并选择对应的步行或驾车服务。连续移动时，系统先让旧请求失效，再合并短时间内的变动。返回结果以后，还会核对它对应的日期、顺序和方式。这样即使早先的请求晚回来，也不会把旧路线绘到新行程上。

### 6:05–6:45 保存、校验和代码复用

> 第三处是保存。浏览器只保存能恢复的行程数据和设置。导入会检查版本、坐标、唯一 ID 和引用，合法后才提交，避免坏文件破坏已有旅行。
>
> 实现时参考了 TREK 的地图拖放和另一个项目的多日拖动思路。实际修改复用的是带 MIT 许可的高德分段请求片段。页面、拖放规则、路线调度和存档校验由本项目实现，来源与许可都在报告里记录。

## 6:45–7:30 成果与扩展

操作：回到规划页或展示项目总结，按计时收尾。

> 目前项目已经能完成从找地点、拖入行程、查看道路与时间，到保存、导出和回看足迹的流程。我们跑过五十五项逻辑测试，也用真实高德服务验证了武汉同一天的驾车与步行，并检查了手机布局和实际生成的 A4 PDF。
>
> 现在每份旅行以单城市为单位，之后可以扩展连续跨城旅行，进一步关联每天所在城市与跨城交通。我的展示到这里，谢谢大家。
